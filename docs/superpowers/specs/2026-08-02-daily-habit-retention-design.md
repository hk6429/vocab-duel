# 字鬥英雄「每日回來學」產品升級設計

日期：2026-08-02  
狀態：待使用者審閱  
目標版本：Habit Loop v1

## 1. 決策摘要

- 第一優先受眾：國中學生。
- 每日核心承諾：5–8 分鐘、10 題。
- 主要策略：健康習慣閉環，搭配少量班級陪伴感。
- 訂閱方式：安裝網站（PWA）＋自願開啟每日 Web Push。
- 提醒時間：學生自行選擇，預設 Asia/Taipei 19:30；每日最多一則。
- 不採用：付費抽卡、無限通知、公開羞辱式排行榜、答錯扣資產、強迫註冊。

每日閉環：

`提醒 → 一鍵進入今日 10 題 → 即時進度 → 完成獎勵 → 明日伏筆`

## 2. 四位專家的設計分工

| 專家視角 | 本案採用原則 |
|---|---|
| Yu-kai Chou／Octalysis | 使命感、進度、選擇權、收藏與驚喜；不靠損失焦慮當主引擎 |
| Nir Eyal／Hook Model | 提醒是觸發器，10 題是行動，學習成果是獎勵，明日目標是投入 |
| BJ Fogg／Behavior Model | 降低啟動難度、在學生有能力完成時提醒、讓行動入口清楚到不必思考 |
| Duolingo／Luis von Ahn | 短回合、連續學習、分級難度、回歸保護與可看見的每日完成狀態 |

## 4. 介面與流程

### 4.1 首頁資訊層級

1. 英雄身分與連續學習狀態。
2. 「今日 10 題」主卡：剩餘題數、時間、今日獎勵、一鍵開始／繼續。
3. 七日章回與 5／7 週目標。
4. 詞靈、文學家、單字之城等自由探索入口。
5. 每日任務細項與其他工具收在第二層，降低首頁決策負荷。

### 4.2 訂閱漏斗

1. 學生完成第一次今日 10 題。
2. 結算畫面說明「明天可從主畫面直接繼續」。
3. 引導安裝；成功或學生自行完成後才顯示通知邀請。
4. 學生選擇提醒時間並主動點擊「開啟每日提醒」。
5. 系統請求通知權限並建立 PushSubscription。
6. 設定頁可查看狀態、改時間、暫停或完全刪除訂閱。

## 5. 技術設計

### 5.1 前端模組

- `manifest.webmanifest`：名稱、圖示、`start_url`、`id`、`display: standalone`、捷徑。
- `sw.js`：離線殼層、Push 事件、notificationclick 深連結、版本更新。
- `js/dailyquest.js`：每日題組、續答、10 題結算、週章回。
- `js/install.js`：安裝能力偵測、平台教學與安裝邀請冷卻。
- `js/push.js`：權限前導、訂閱建立、提醒時間、停用與匿名事件。

### 5.2 伺服器與排程

- 以現有 Cloudflare Pages Functions 作為單一 Push API，三個正式網域共用。
- 使用現有 Upstash Redis 保存加密後的 PushSubscription、時區、提醒時間、最後派送日與 90 天到期日。
- 不保存姓名、Email、班級、作答內容或完整學習紀錄。
- GitHub Actions 每 15 分鐘呼叫受 secret 保護的 dispatch endpoint；只派送當前時段、尚未完成且未取消者。
- VAPID 私鑰與 dispatch secret 只放平台 Secrets，不進 Git。
- 訂閱 endpoint 視為機密能力網址；API 需做來源 allowlist、輸入驗證、速率限制與 CSRF 防護。

### 5.3 完成狀態同步

- 今日任務完成後，前端向 Push API 寫入 `doneDate`，讓當日排程跳過。
- 離線完成時先寫本機 outbox，下一次連線補送；重複請求以日期＋匿名裝置 ID 保證冪等。
- 三個網域各有獨立瀏覽器儲存；通知紀錄保存原始允許網域，深連結回訂閱建立時的網域。

## 6. 隱私與健康遊戲化

- 國中生不需建立帳號，不蒐集真實姓名、電話、Email 或精確位置。
- 通知必須由直接點擊觸發授權；不同意仍可完整使用網站。
- 每日最多一則、22:00 後不派送、不使用「連勝要斷了」等焦慮文案。
- 可一鍵暫停七天或完全刪除訂閱；伺服器收到 404／410 push endpoint 後立即刪除。
- 排行榜不顯示未完成者，不用同儕壓力懲罰學生。

## 7. 錯誤與降級

- 不支援 Push：仍提供 PWA 安裝、主畫面捷徑、站內明日提醒與下載行事曆提醒。
- iOS 尚未安裝：顯示加入主畫面的逐步教學，不直接要求通知。
- 權限 denied：記錄本機冷卻 30 天，不反覆彈窗；設定頁仍可說明如何手動恢復。
- 推播 API 離線：今日任務與獎勵照常；訂閱操作顯示可重試狀態。
- 排程延遲：超過使用者時段 30 分鐘或晚於 22:00 即跳過，不補轟炸。

## 8. 測試與發布門檻

- 單元測試：題組 5/3/2 組成、跨日重置、續答、冪等結算、5/7 週章。
- Service Worker 測試：安裝、更新、離線首頁、push、notificationclick。
- API 測試：subscribe/update/unsubscribe/done/dispatch、來源 allowlist、速率限制、404/410 清除。
- 瀏覽器驗收：Android Chrome、桌面 Chrome、iPhone 主畫面 Web App；不支援情境也必須降級可用。
- 無障礙：主卡鍵盤操作、進度語意、通知設定標籤、動態回饋 `aria-live`。
- 回歸測試：既有閃卡、每日任務、連續天數、護盾、召回、詞靈、城鎮與三平台發布不得退步。
- 正式部署：GitHub 單一乾淨提交後同步 Vercel、Cloudflare Pages、Netlify，逐站 cache-busting 回讀。

## 9. 成功指標

以發布前 14 天為基準，發布後觀察 28 天：

- 首次 10 題完成率提升至少 15%。
- 完成首輪者的安裝引導開啟率至少 20%。
- 安裝者的通知自願開啟率至少 35%。
- 通知點擊後 10 題開始率至少 45%。
- 每週完成 5 天的學生比例提升至少 20%。
- D7 回訪率提升至少 15%，同時通知停用率低於 10%。

若通知停用率、拒絕率或回報干擾比例偏高，優先減少提醒，不以更多通知追數字。

## 10. 實作切分

本規格是一個產品目標，但實作分成三個可獨立驗收的階段：

1. 今日 10 題＋首頁閉環＋週章回（01、06–25）。
2. PWA 安裝與離線能力（02–05、26）。
3. Web Push、提醒設定、匿名量測與排程（27–30）。

每階段都先補測試、再實作、再做實際瀏覽器驗收；第三階段完成後才宣稱「每日通知訂閱」正式可用。

## 11. 技術依據

- [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)：背景推播需要 active service worker，PushSubscription endpoint 必須視為機密。
- [WebKit：iOS／iPadOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)：iOS 主畫面 Web App 才能請求 Web Push，且權限請求必須回應直接使用者操作。
- [WebKit：Badging for Home Screen Web Apps](https://webkit.org/blog/14112/badging-for-home-screen-web-apps/)：主畫面 Web App 可在通知授權後顯示徽章。
- [web.dev PWA Installation](https://web.dev/learn/pwa/installation)：Manifest 與安裝後 standalone 體驗的基本要求。
